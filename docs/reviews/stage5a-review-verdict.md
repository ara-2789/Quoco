# External review verdict — Stage 5a design (PR #291, reviewed at head 744d0d1). Received 2026-09-17. Recorded verbatim below; not edited.

Package read in full at PR #291 head `744d0d1` — all nine decisions, §8, both revision layers, the UNVERIFIED section — and the migration question answered from the applied files rather than the package's assertion: both photo tables carry `FOR SELECT TO authenticated` policies and SELECT grants (`044:292-293,316`; `043:259,291`), so every read path 5a needs already exists in the catalog. **Verdict: GO, design tier, with the conditions embedded in the answers below.** Your seven questions, then the asserted-vs-verified flags.

**Q1 — redirect is acceptable; streaming buys less than it costs.** The exposure delta is a 5-minute, single-object signed URL in the network layer of *the authenticated PM's own browser* — the person the URL authorizes is the person who can see it; the residual vectors (history sync, shoulder-surf) are TTL-bounded and narrower than the email path, which embeds the actual bytes. Streaming would route every image's bytes through a Vercel function — memory, latency, and double bandwidth per photo, on a page D2 deliberately leaves uncapped — to close a channel that's already inside the trust boundary. Keep the redirect, keep `no-store` on the route, keep URLs out of HTML (D6 already does), and reuse the 5-minute TTL. Accepted as designed.

**Q2 — no, timing uniformity is not required, and here's the principle so it doesn't get re-litigated:** the one-failure-shape doctrine exists to deny an *enumeration oracle*, and the UUID keyspace already denies enumeration — a timing difference tells an attacker-with-a-valid-session that some unguessable id exists somewhere, which is information worth nothing. Padding timing costs real UX (artificial delays) or impractical constant-time DB patterns. Match status, body, *and headers* (a `cache-control` difference between failure paths would be its own tell); let timing float. `photo-access.ts`'s own design never promised timing, only shape.

**Q3 — yes, cleanly separable, with one ordering requirement stated explicitly.** F1's early-return has two observable properties: zero Storage calls and zero candidate-row queries when unready. The shared "which photos" core is pure DB selection (downloads and caps are already part (b)), so the Storage half is trivially preserved — but the zero-*queries* half is preserved **only if the email wrapper gates before calling the core**. Gate-first in the wrapper, core untouched by readiness, and F1's observable behavior is byte-preserved; wrapper-calls-core-then-gates would silently change the query-count property the retry-by-throw path currently has. Nothing in F1 is load-bearing *inside* the selection itself — the gate reads readiness state the selection never touches. With D7's zero-edit hard condition on both Stage-4 test files, the split is safe.

**Q4 — absorb and retire.** `getSignedPhotoUrl` has zero production callers, speaks only 3-segment paths, and lacks D5's tenant check; keeping it alongside D6 creates two parallel signing barriers, which is precisely the dual-copy divergence class this module's boundary-agreement test was built to prevent. D6's route becomes the one barrier; `getSignedPhotoUrl` is deleted or reduced to an internal helper the route calls; and — **this is the 044 condition falling due** — the boundary-agreement fixture matrix extends to the hindrance cases and re-targets the route's authorization function as its TS side, since that function is now the thing that must agree with RLS. The package's phrase "join shapes already proven correct by the RLS policies" is the one place §4 asserts more than it has: proven for RLS-as-user, yes — but D6 *re-implements* those joins in TS under service_role, which is a new copy, and the extended matrix is what proves the copy, not the citation.

**Q5 — per-IP is the wrong axis, as you suspected; per-user is right, sized for page bursts.** An authenticated per-photo route's abuse unit is the session, not the address — and the limiter must accommodate a legitimate DPR render firing dozens of near-simultaneous calls (D2 uncapped), so a generous per-user fixed window (order of 100+/min), reusing the confirm-email in-memory pattern with its named per-instance limitation, is proportionate now. Don't batch-sign — that reintroduces URLs-in-page-payload, which D6 rightly forbids. The real amortization lever, named for when §8's cost shape becomes a measured number: memoize the *authorization* (the per-`(user, project)` PM check) per request or short-TTL, not the URLs — cuts the repeated join while keeping every photo's row check intact.

**Q6 — no migration, confirmed with evidence the package couldn't run:** both tables' authenticated SELECT policies and grants exist in the applied 043/044 files (cited above), 047 left SELECT untouched, D6's own reads go through service_role where RLS is moot, and D5's tenant check plus the shared PM function are TypeScript. Nothing in 5a touches the catalog. The package's position holds.

**Q7 — yes, and make it the finding it deserves to be.** The `canEditLog` bug is the third instance of the wrong-column class (039's review established `project_members.role`; your D3 citation chain now proves the two columns disagree *by construction* — project creation writes `pm` to membership while onboarding writes `admin` to `users`), and §8's framing is exactly right: the failure mode is D3's designed behavior wearing a bug's consequences, silent and correct-looking. One `lib` function — `isProjectPm(userId, projectId)`, explicit project parameter, auth-resolution via the `auth_id` join shape per the `handle_new_user` drift lesson — used by D3, D6, and the later correction-gate fix. **Plus the test that makes the wrong column unwritable: a fixture user shaped like your real prod PM — `users.role = 'admin'`, `project_members.role = 'pm'` — who must see photos.** Any future implementation reaching for `profile.role` fails that fixture instantly. That's fix-a-pattern applied prospectively, before the third copy exists.

**Asserted-vs-verified flags, as requested — and the package makes this easy by being honest about most of it.** The UNVERIFIED section is the right artifact: no invented numbers for D6's cost, the D5 fixture's insertability deferred to rehearsal, prod state explicitly unprobed, and the same-tenant non-PM case scoped to test-db-only proof. Beyond the Q4 item above (RLS-proven joins ≠ TS-copy-proven), two more: D3's "no section at all" is correctly flagged in §8 as *new behavior with no existing choke point* — per-page enforcement of an absence is exactly the kind of claim that will look done when it's half-done, so §7's tests should assert the absence on *every* page, not the first one built; and the six-string table's recorded-vs-new split (two in the design doc, four new) is the approved-strings discipline working — hold the "no new strings" line during build. The D9 decision — pages never wait, only the email keeps its gate — is the right asymmetry and correctly re-scoped Q3 from semantics to mechanics before I had to.
