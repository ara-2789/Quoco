**Columns checked**: `timing`, `timing_raw` (036, `hindrances`), `pm_notified_at` (037,
`hindrances`), `submitted_via` (036, `hindrances` — an existing column, default dropped).

**Method**: `grep -rn` across `lib/`, `app/`, `test/` for each column name, then manually

`pm_notified_at` both exist on more than one table (`safety_incidents`, `invoices`,
`hindrances`), so a name match alone does not mean a `hindrances` match. Confirmed
`hindrances` itself has zero application-code `.from('hindrances')` call sites anywhere
in `lib/` or `app/` before checking individual columns.

Three tables carry this column (`safety_incidents`, `invoices`, `hindrances` — all from
migration 001). 036 touches only `hindrances.submitted_via` (`ALTER COLUMN submitted_via
DROP DEFAULT`, fixing a pre-existing bug: `DEFAULT 'whatsapp'` was never a member of
`hindrances`' own CHECK set `('whatsapp_scheduled', 'whatsapp_adhoc', 'web_app')`).

  code; a comment goes stale.** This test inserts into `hindrances` explicitly setting
  `submitted_via: 'whatsapp_scheduled'`, with its own comment (lines 302-306) reading:
  *"submitted_via is set explicitly here. hindrances.submitted_via carries a latent 001

  no longer exists at all (036 drops it outright), so the comment's framing ("a latent
  bug... out of scope") becomes stale the moment 036 lands: there is no longer a bug to
  describe, out of scope or otherwise. **Action for whoever applies 036**: update this

- **`test/migration-016.test.ts:54`** (`afterEach` cleanup, `db.from('hindrances').delete()...`)
