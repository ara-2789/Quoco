## 5. Findings

### S-3. Caller-supplied timestamps are accepted at the allowed transitions (proven)

**What breaks**
- X3: moving a DC into `approved` with `approved_at = now() + 5 days` was accepted.
- X4: moving into `rejected` with `rejected_at = now() + 30 days` was accepted.
- The only bound is `>= created_at`. The same shape applies to `cancelled_at`, to `unlinked_at` in TR3, and to `engineer_ack_at` in TR5.

**Why it matters**
- `engineer_ack_at` and `linked_at` drive the 30-day clock (D-12, D-14). A wrong value silently moves "overdue".
- It's the same "wrong stamp impossible, not merely uncaught" reasoning behind 043's generated `expires_at` and B2's snapshot overwrite.
- Who approved is now locked. When is still caller-chosen.

**Why S, not B:** only a PR-B definer function can reach this. The damage is a wrong time, not a wrong actor, and the clock it moves is display-only.

**Fix**
- At each allowed transition, the trigger overwrites the timestamp with `now()`: `approved_at`, `rejected_at` and `cancelled_at` in TR4, `unlinked_at` in TR3, `engineer_ack_at` in TR5.
- This follows TR3's existing "overwrite, never trust NEW".
- `received_at` stays caller-supplied by design (D-25).
- If you'd rather keep caller time for a future backfill path, record that as a decision instead.

**Test** (T-TRIG): a future-dated value at each transition gets stored as the transaction time. RED against `668956e`.

### N-3. A positive control can pass on 0 rows

- `t.expect(…, 'ok')` passes when an UPDATE matches 0 rows. The T-TRIG knock-ons show that ids can drift inside a scenario.
- Expected *refusals* fail safe in that case, as the RED showed. A positive control does not.
- Add `GET DIAGNOSTICS … ROW_COUNT` to `t.expect` and fail an `'ok'` DML that touched 0 rows.
