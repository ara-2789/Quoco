### 4.9 D13 SETTLED — the board rule, restated on episodes (rev9)
**Decision (Aravind, 19 Sep 2026):** in this slice; dated; **not** a status filter. A deactivated engineer stops being expected from the deactivation date onward — today's board, the Today "Needs your attention" list and its heading count, every later date — and **history is not erased**: every earlier date, and every log the engineer submitted, is unchanged. *(rev7 keyed this on `users.deactivated_at`; rev8 added `reactivated_at`; **rev9 keys it on episodes, §2.8** — struck below where it mattered.)*
**A plain `WHERE users.status = 'active'` is WRONG here.** `users.status` is *current state*. The board iterates the roster **per date** and shows a log only through a roster entry (`query.ts:226-260`), so a status filter applied while the PM looks at last Tuesday drops last Tuesday's card and the log submitted that day. **The rule, against episodes.** For a roster entry (engineer E on project P) and a board date L (IST `'YYYY-MM-DD'`), with `eps` = E's episodes on P:
1. **`eps` empty → expected** (a legacy engineer or a directly-inserted membership; behaviour unchanged).
2. Otherwise **expected ⟺ some episode has `istDate(opened_at) ≤ L` and (`closed_at` NULL or `L < istDate(closed_at)`)** — equivalently, E was in an open episode **at the end of IST day L** (`opened_at < start of IST day L+1` and (`closed_at` NULL or `closed_at ≥` that instant)).
- **Which episode bounds a date:** at most one — the open one and closed ones do not overlap (§2.8) — the one whose IST-day span `[istDate(opened_at), istDate(closed_at))` contains L. **The opening day is included; the closing day is excluded** (so the deactivation day D is excluded, as D13 says, and a reactivation day R is expected). An episode opened and closed on the same IST day is an empty span.
- **A date inside a gap between episodes is not expected.** So is a date before the first episode and a date after the last close. Not expected + no log ⇒ **the entry is omitted**. Not expected + a log exists ⇒ **the card is kept, `afterDeactivation: true`** (D14 i). *(The field keeps its rev7 name; it now means "this date lies outside every episode".)*

## 11. For Aravind — run against PROD (not run by me) — episodes plan queries

Read-only; confirm the project ref first. *(`b1` and `b2` are new in rev11: they size and guard the R1 backfill.)*
```sql
-- (v2) legacy deactivated engineers on prod: after 048 they have NO episode, so the board keeps showing them as today and a later reactivation materialises a closed 'backfill' episode (§2.8);
--      also shows whether any 'pending' users exist (the rule must not touch them)
SELECT u.role, u.status, count(*) AS n FROM users u WHERE u.status <> 'active' GROUP BY 1, 2 ORDER BY 1, 2;

-- (n3) engineers with MORE THAN ONE engineer membership on prod — the real, defended state; why the episodes backfill is lazy, never an eager INSERT…SELECT (§2.8)
SELECT user_id, count(*) AS engineer_memberships FROM project_members WHERE role = 'engineer' GROUP BY user_id HAVING count(*) > 1;

-- (u2) AFTER/BEFORE 048: is the table name free on prod?
SELECT to_regclass('public.engineer_episodes') AS engineer_episodes_exists;

-- (e1) AFTER 048 only — invariant I1 drift: engineers whose status and open episodes disagree (§2.8)
SELECT u.id, u.status, count(e.id) FILTER (WHERE e.closed_at IS NULL) AS open_episodes, count(e.id) AS episodes
FROM users u JOIN engineer_episodes e ON e.user_id = u.id
WHERE u.role = 'engineer'
GROUP BY u.id, u.status
HAVING (u.status = 'active' AND count(e.id) FILTER (WHERE e.closed_at IS NULL) <> 1)
    OR (u.status = 'deactivated' AND count(e.id) FILTER (WHERE e.closed_at IS NULL) <> 0);

-- (b1) SIZES the slice-2 backfill (R1): engineers created by slice 1 (registered_at set), by status, with their engineer-membership counts. Run on prod AFTER slice 1 is applied and BEFORE slice 2 is applied.
SELECT u.status, count(DISTINCT u.id) AS engineers, count(pm.id) AS engineer_memberships
FROM users u LEFT JOIN project_members pm ON pm.user_id = u.id AND pm.role = 'engineer'
WHERE u.role = 'engineer' AND u.registered_at IS NOT NULL GROUP BY u.status ORDER BY u.status;

-- (b2) the ABORT CONDITIONS of the R1 backfill: any slice-1 engineer that is not active, or that has more than one engineer membership. EXPECTED: zero rows (PROCEED); any row is STOP.
SELECT u.id, u.status, count(pm.id) AS engineer_memberships
FROM users u LEFT JOIN project_members pm ON pm.user_id = u.id AND pm.role = 'engineer'
WHERE u.role = 'engineer' AND u.registered_at IS NOT NULL GROUP BY u.id, u.status
HAVING u.status <> 'active' OR count(pm.id) > 1;
```
