No parameter defaults (`CLAUDE.md:361-372`). `p_engineers` is an array of `{ name, whatsapp_number }`, the number **already validated and normalised by TypeScript** (§3); the function asserts only the generic stored shape (§3.6).

Return `{ applied: boolean, rows: [ { idx, status, … } ] }`. Status values are machine identifiers, not wording. **Allowed fields per status — the whole payload:**
| status | fields | note |
|---|---|---|

### 2.2 The dry-run flag (D7)
`p_dry_run = true`: authorisation, tenant binding, argument validation and **full classification**; returns the payload apply would; **writes nothing**. **Why it exists, plainly:** without it a cross-tenant collision is invisible at preview (under RLS a preview reads only its own tenant's `users`, probe j `users_select`) and **aborts the whole all-or-nothing batch at apply**; with it, preview and apply run the *same code path* and the collision is caught at preview, generically.
1. **Authorisation runs BEFORE any number lookup, in both modes.** 2. **Cross-tenant collisions are `number_registered`**: exactly `{idx, status}` (T5). 3. **Apply re-runs every check** and never trusts the preview's verdicts. 4. Dry-run writes nothing (T7).

### 2.3 Order of operations (one transaction)
1. **Resolve the caller:** `users` where `auth_id = auth.uid()` (`019:170-171`; probe p); none → `insufficient_privilege` (`019:172-175`). `auth.uid()` is never compared to `users.id` (`007:127`, `007:60-67`, `007:76-78`); engineers/owners have `auth_id` NULL (`CLAUDE.md:833-840`).
2. **Load the project; tenant-bind NULL-safe.** Missing, **or** `project.tenant_id IS DISTINCT FROM caller.tenant_id` → `no_data_found`, one indistinguishable error (`019:219-222`); `projects.tenant_id` is NOT NULL (`001:55`). **This single comparison is the only tenant-binding mechanism** (T1).
3. **Role/authority gate (§1)**, else `insufficient_privilege`. 4. **Validate the argument:** 1..50 rows (`program_limit_exceeded`, `019:208-212`); non-empty `name` ≤ 100; generic-shape number; duplicates → `invalid_parameter_value`.
5. **Classify every row** (R5–R7, §4). 6. If `p_dry_run`, or **any** row is not `ok` → write nothing. 7. Otherwise insert per row (§2.6); any exception rolls back everything; a concurrent add of the same number loses on `UNIQUE (whatsapp_number)` (`001:44`, probe h; `23505`).
**The NULL trap in the precedent (deferred):** `019:230` is `IF v_tenant_id <> get_user_tenant_id()`; a NULL tenant makes it NULL and the guard passes (masked by `019:224-229`). The new function does not copy it.

**Lifecycle.**
- **Opens on add:** `add_engineers_to_project` inserts, per row, the `users` row, the `project_members` row **and one episode** (`opened_by` = caller, `opened_via = 'added'`, `opened_at = now()`).
- **Opens on reactivate:** `reactivate_engineer` sets `users.status = 'active'` **and** inserts an episode (`'reactivated'`).
- **Closes on deactivate:** `deactivate_engineer` sets `users.status = 'deactivated'` **and** closes the engineer's open episode on this project (`closed_at = now()`, `closed_by` = caller, `closed_via = 'deactivated'`).
- **Legacy engineers — every engineer that exists today has NO episode — are materialised lazily, on first touch, never by a migration backfill.** Deactivating a legacy *active* engineer first inserts an episode `(opened_at = project_members.created_at, opened_by NULL, opened_via 'backfill')`, then closes it as above. Reactivating a legacy *deactivated* engineer (deactivated before 048, so no recorded start) inserts a **closed** `'backfill'` episode `[project_members.created_at, R)` — the board keeps showing the pre-048 gap as it does today ("past dates unchanged") — and then the new open episode at R. **Why lazy, a finding:** an eager `INSERT … SELECT` backfill would create one open episode **per engineer membership**, and the real, defended state "one engineer, two `engineer` memberships" (§4.10) would violate `uq_engineer_episodes_one_open` and **abort the migration**; prod's count of such engineers is unread (§11 `n3`). Lazy materialisation writes no data in the migration, so the additive-backfill rule machinery (`CLAUDE.md` §6) is not tripped. Alternative, not chosen: eager backfill guarded by a pre-check that no engineer has two memberships.
**What enforces "at most one open episode per engineer".** **The database:** the partial unique index above — race-proof; the second of two concurrent opens gets `23505`. **The functions:** after the §2.7 helper resolves the caller, each locks the target `users` row `SELECT … FOR UPDATE` before reading or writing episodes, so concurrent deactivate/reactivate serialise; both then write `users.status` and the episode in **one transaction**. **Not DB-enforced, named:** non-overlap of *closed* episodes (an `EXCLUDE USING gist` needs `btree_gist`; availability unread, UNKNOWNS #39) — the functions always open at `now()` at or after the last close, and the CHECK forbids `closed_at < opened_at`. **Two records must agree** (the price of keeping `users.status`, which every roster reads): invariant **I1** — `status = 'active'` with any episode ⇒ exactly one open; `status = 'deactivated'` ⇒ none open. The functions maintain it; T34 asserts it after every step; §11 `e1` is the drift probe for prod. **This index is not the D12 index:** it is on a table only the definer functions write, so the 7 test files of §4.7 (which insert `project_members` rows directly and never episodes) are untouched; the D12 rider stays as pinned (§4.10).

## 3. Phone numbers and the validator

### 3.1 The chain
`route.ts:111`: `fromNumber = normalisePhoneNumber(params.From ?? '')`; `route.ts:130-133` looks up `.eq('whatsapp_number', fromNumber)`. Inbound form: `+` + digits, no `whatsapp:` prefix, no separators (`normalise.ts:13-15,18,21-23`); downstream passes it through verbatim (`dispatch.ts:180,199,217`; `inbound-start.ts:463,852`; `session.ts:58,91`). **No mismatch with the prod stored form** (`+` + 12 digits) provided the screen stores `normalisePhoneNumber(raw)` output only. That real Twilio sends `whatsapp:` + E.164 rests on a comment (`normalise.ts:4`) and fixtures (`test/webhook.test.ts:263`).

### 3.2 Status of the validator — the consequence, stated explicitly
`normalise.ts` **never rejects anything** (`normalise.ts:40-42`), and **no validator exists anywhere in the repo** (the phone `git grep`; the one schema CHECK is `outbound_sends_to_phone_number_check`, `031:478-479`, probe q). `links.ts:10-11` and `reactivate-copy.ts:48-52` say the guarantee "lives upstream at the write paths"; grep g5: no engineer write path exists, so this screen is the first.
**Consequence:** without a validator, a mistyped line stores a well-formed-looking row that can never match an inbound message (the webhook compares the *normalised inbound* number, `route.ts:133`) and **permanently holds that value under the global unique** (`001:44`), with no removal path in this slice (§2.9). The executed probe shows what `normalisePhoneNumber` alone would have stored for the rejected classes: letters gain a `+`, the empty string becomes `"+"`, a too-short value gains one, trailing text is kept, a `00`-prefixed form keeps its zeros.

### 3.3 Validation happens BEFORE normalisation — the exact rule
On each raw pasted token: **V1 charset** — only ASCII digits, `+`, whitespace, `-`, `(`, `)` (`normalise.ts:18`'s separators); anything else rejects. **V2** remove whitespace, `-`, `(`, `)` → `t`. **V3** `t` must match exactly one of `S1 ^\+91[6-9][0-9]{9}$`, `S2 ^91[6-9][0-9]{9}$`, `S3 ^0[6-9][0-9]{9}$`, `S4 ^[6-9][0-9]{9}$`. Then call `normalisePhoneNumber(raw)` and **assert** the result matches the single stored form **`^\+91[6-9][0-9]{9}$`** (13 characters) and is a fixed point.
**Reuse, not reimplementation:** import `lib/whatsapp/normalise.ts:9`; never edit or copy it. **Evidence (throwaway probe, re-run in this log):** 34 inputs (14 accepted, 20 rejected), **0 violations**.

### 4.9 D13 SETTLED — the board rule, restated on episodes (rev9)
**Decision (Aravind, 19 Sep 2026):** in this slice; dated; **not** a status filter. A deactivated engineer stops being expected from the deactivation date onward — today's board, the Today "Needs your attention" list and its heading count, every later date — and **history is not erased**: every earlier date, and every log the engineer submitted, is unchanged. *(rev7 keyed this on `users.deactivated_at`; rev8 added `reactivated_at`; **rev9 keys it on episodes, §2.8** — struck below where it mattered.)*
**A plain `WHERE users.status = 'active'` is WRONG here.** `users.status` is *current state*. The board iterates the roster **per date** and shows a log only through a roster entry (`query.ts:226-260`), so a status filter applied while the PM looks at last Tuesday drops last Tuesday's card and the log submitted that day. The boundary must be a **date**, and the only per-date facts are the episodes. (`status` is right in exactly one place — the project-detail team list, which has no date dimension.)

**The rule, against episodes.** For a roster entry (engineer E on project P) and a board date L (IST `'YYYY-MM-DD'`), with `eps` = E's episodes on P:
1. **`eps` empty → expected** (a legacy engineer or a directly-inserted membership; behaviour unchanged).
2. Otherwise **expected ⟺ some episode has `istDate(opened_at) ≤ L` and (`closed_at` NULL or `L < istDate(closed_at)`)** — equivalently, E was in an open episode **at the end of IST day L** (`opened_at < start of IST day L+1` and (`closed_at` NULL or `closed_at ≥` that instant)).
- **Which episode bounds a date:** at most one — the open one and closed ones do not overlap (§2.8) — the one whose IST-day span `[istDate(opened_at), istDate(closed_at))` contains L. **The opening day is included; the closing day is excluded** (so the deactivation day D is excluded, as D13 says, and a reactivation day R is expected). An episode opened and closed on the same IST day is an empty span.
- **A date inside a gap between episodes is not expected.** So is a date before the first episode and a date after the last close. Not expected + no log ⇒ **the entry is omitted**. Not expected + a log exists ⇒ **the card is kept, `afterDeactivation: true`** (D14 i). *(The field keeps its rev7 name; it now means "this date lies outside every episode".)*
- ~~rev7/rev8: `isAfterDeactivation(status, deactivatedAt, reactivatedAt, logDate)`, "`deactivated_at` NULL ⇒ legacy", and the `status`-guard bullet~~ — **struck**: with no `deactivated_*`/`reactivated_*` columns there is nothing to guard. `pending` users are not touched (no episode).
- **IST, not UTC.** Executed on the real helpers (rev7 log, `ist-boundary.mjs`, re-run in rev9): an instant `2026-09-19T18:30:00+00:00` has IST date `2026-09-20` (UTC slice `2026-09-19`); `istDateString` (`date.ts:27-36`) and `istParts(…).date` (`status.ts:47-61`) agree; the Postgres microsecond form parses. Comparing zero-padded date strings is chronological and is already how `query.ts:622` orders dates. A UTC slice mis-dates every open/close in 18:30–24:00 UTC (T23).
- **Consequence to flag (D18):** for an engineer **with** episodes, dates before their first episode are not expected — so an engineer added today no longer reads amber "Not checked in" on yesterday's board (the wart noted in §4.8: "a newly added engineer also shows amber on past dates before they joined"). This is the leave-side twin of the join-side rule already in the DPR (`dispatch.ts:427-428`, `joined_late`). Legacy engineers (no episodes) are unchanged.
- **"Any future date":** the Daily Logs page clamps to today (`daily-logs/page.tsx:40-41`) and Today reads today only (`dashboard/page.tsx:116`); `getDailyLogsBoard` itself accepts any `logDate` (T24a uses "tomorrow").
